# Internationalization (i18n)

All user-facing text is looked up by key from `src/locales/<locale>.json`. English
(`en.json`) is the source; `ja`, `ko`, `ru` and `zh` are translations of it. Any key a
locale is missing falls back to English at runtime.

English ships in the main bundle (about 25 KB gzipped) and is in the locale store from
the first render, so a key never shows up raw while the app boots. The other locales load
lazily when selected.

## Using a string

```ts
const { t, tv } = useI18n()

t('cohortDefinitions.saveBeforeGenerate')          // ComputedRef<string>, reactive
tv('cc.viewEdit.results.threshold.showAtLeast', { n: 5 })  // plain string
```

- **No inline English.** Write `t('key')`, not `t('key', 'Save')`. English is in en.json
  and is loaded before the first render, so an inline fallback is never shown. It only
  drifts from the real copy. `npm run i18n:check` fails on any inline fallback for a key
  en.json has. `--fix` strips the ones that repeat en.json exactly. A fallback whose
  wording differs is reported and never stripped. It usually means the call site wants
  its own key; otherwise update en.json.
- **Placeholders are `{name}`**, passed as params: `t('x.y', { count })`. Do not
  concatenate translated fragments (`t('a') + ' ' + n`), because word order differs
  between languages.
- **One key per meaning.** Never borrow a key because its English happens to fit. For
  example, an error-page title must not reuse "The Source was not saved. {message}". The
  English of the key you borrow can change, and translators translate it for its own
  context.

## Naming keys

`<feature>.<area>.<element>` in lowerCamelCase, named after what the string is for:

| Good | Bad |
|---|---|
| `components.cohortExpressionEditor.eraCollapseGap` | `components.cohortExpressionEditor.cohortErasText_1` |
| `cohortDefinitions.conceptSetPicker.empty` | `cohortDefinitions.textfield_17` |

`i18n:check` rejects numbered keys (`…Text_3`, `…_17`, `textfield`).

**Shared vocabulary** lives under `common.*` (actions such as Save, Cancel and Delete,
generic nouns such as Name and Description) and `columns.*` (table headers). Only reuse a
shared key when the meaning is identical, not just the English. A word that is the same
in English can need a different translation elsewhere (gender, case or counters in
ru/ja), so feature-specific phrasing gets its own key.

## Adding or changing text

1. Use the key in code: `t('feature.area.element')`.
2. Add the English to `src/locales/en.json`. Shortcut: write
   `t('feature.area.element', 'English text')` and run `npm run i18n:check -- --backfill`.
   It moves the fallback into en.json and strips it from the call.
3. `npm run i18n:check` must pass. It runs in `npm run check-all`.
4. Translations: see below. Changing the English of an existing key marks its
   translations stale. That is intended, but if the meaning changes, use a new key
   instead.

## Translation workflow

`.i18n-manifest.json` records, per locale, which English text each string was translated
from. A translation becomes *stale* when its English changes and *new* when there is none
yet.

```sh
npm run i18n:status                # new / stale / removed per locale
npm run i18n:extract -- ja         # writes .i18n-work/ja/delta.json ({id: english})
# translate into .i18n-work/ja/delta.translated.json ({id: translation})
npm run i18n:apply -- ja           # merges, prunes removed keys, updates the manifest
```

The same loop works for `ko`, `ru` and `zh`. They were imported from WebAPI's Atlas 2.x
bundles (commit `c079f520`). A translation from that import is tracked as in sync only
when its English is still the text it was translated from
(`node scripts/i18n-refactor.mjs adopt <code> c079f520`). Everything else is reported
as new.

## Refactoring keys

Never rename or delete keys by hand. i18n-sync tracks translations by key, so a hand
rename silently drops the key's translation in every locale. Use the codemods, which
update en.json, every translated locale, the manifest and `src/`/`tests/` together:

| Command | What it does |
|---|---|
| `npm run i18n:unused` | Lists keys nothing in `src/` or `tests/` references (`-- --list` for the keys) |
| `npm run i18n:dups` | Referenced keys that share the same English |
| `npm run i18n:prune` | Deletes every unused key from all locales, and translated keys en.json does not have |
| `npm run i18n:rename -- <map.json>` | Applies `{ "old.key": "new.key" }`. If the new key exists with the same English, the two are merged. Refuses anything that would change copy |
| `node scripts/i18n-refactor.mjs restore <map.json> <git-ref>` | Re-adds `{ "new.key": "old.key" }` from an older commit, translations included. Use it to revive a pruned string |
| `node scripts/i18n-refactor.mjs recover <code> <git-ref>` | Fills keys a locale lacks with the `<git-ref>` translation of identical English (in-sync translations only) |
| `node scripts/i18n-refactor.mjs adopt <code> <git-ref>` | Records translations as in sync when their English/translation pair existed at `<git-ref>` |

Keys built at runtime (`` `versions.errors.${code}` ``) are invisible to the scanner.
Add their prefix to `DYNAMIC_PREFIXES` in `scripts/i18n-usage.core.mjs`, or prune will
delete them. Applied maps are kept in `scripts/i18n-maps/` as a record.

## Plugins

Plugins receive `t(key, defaultValue)` bound to the host translations
(`src/plugins/host/parcelLoader.ts`). Host keys are not a stable API: they are renamed
and pruned along with the host UI. A plugin should ship its own strings and pass a
default. In dev builds the bridge logs a warning, once per key, when a plugin asks for a
host key that does not exist.

## Tests

Assert translated text through `tr('key', params?)` from `tests/helpers/i18n-mock.ts`,
not hard-coded English. See rule 7 in the [testing guide](testing-guide.md).
